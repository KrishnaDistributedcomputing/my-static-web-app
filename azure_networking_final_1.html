Problem Definition

Problem Definition

This section precisely defines the problem being investigated — the gap between what a team requires from Azure networking and what the Azure platform is capable of providing. It establishes the full context before any technical analysis.

Who Is Affected

A team operating a legacy Azure-hosted workload originally deployed when Azure's IP services model was less restrictive in assumptions. The workload serves external customers and business partners who have integrated against a fixed, known IP range at the network level.

What They Need

A contiguous /22 public IP block (1,024 addresses) must remain consistently routable through a Network Virtual Appliance — so that all inbound traffic can be inspected, policy-controlled, and forwarded, while the external IP range stays stable and whitelistable.

Why It Matters

Customer and partner firewalls are configured to permit traffic from this specific /22 range. Changing or fragmenting the range disrupts those whitelists, triggers customer change-control processes, and introduces operational risk to active business relationships.

The Blocker

Azure does not support associating a Public IP Prefix block with a standalone NVA as a single object. The architecture the team relies on — prefix block terminates on NVA — does not exist as a supported Azure construct. This is a platform ceiling, not a configuration problem.

Background & History

The deployment in question originated years ago, at a time when cloud networking assumptions were often carried over directly from on-premises practice. In data centres and co-location environments, owning a public IP prefix meant you could advertise it from any device capable of BGP, terminate it on any NVA or firewall, and manage it as a single routing object. This model is well-understood, flexible, and widely used.

When this workload was first deployed to Azure, it was reasonable to assume that this model would translate. The prefix was allocated, an NVA was provisioned, and the architecture was built on the assumption that the prefix block would route to the NVA. Over time, as the platform evolved and the team grew around this assumption, the dependency on this routing model became embedded — in customer contracts, firewall configurations, operational runbooks, and team knowledge.

Original Deployment
Legacy workload provisioned with a /22 public IP block. Architecture designed on the assumption that the prefix would terminate on a dedicated NVA — consistent with on-premises BGP routing practice. Customer integrations built against this IP range.
Customer Integration
External customers and partners whitelist the /22 CIDR range in their perimeter firewalls, edge routers, and application-layer allow-lists. This becomes a stable dependency that changes through formal change-control processes — not quickly or easily.
Platform Assumption Unexamined
The routing assumption goes unchallenged while the workload operates. Day-to-day operations do not surface the architectural dependency — until an infrastructure review, migration, or scaling event requires the team to deliberately interrogate how the routing actually works.
The Discovery
Technical review confirms the constraint: Azure does not route the /22 to the NVA as a prefix block. The Azure fabric routes individual /32 IPs to resource bindings. The architecture the team assumed they had is not the architecture Azure actually implements. Multiple SME consultations confirm the same finding.
Current State
Decision required: The team must choose between accepting Azure's supported model (individual IP management at scale), moving prefix termination on-premises with hybrid connectivity, or redesigning the external-facing IP strategy entirely. Each path carries business and operational trade-offs.

The Core Problem, Stated Precisely

📌 Problem Statement

A team requires that all inbound traffic for a contiguous /22 public IP prefix be routed through a single Network Virtual Appliance inside Azure, such that the NVA acts as the authoritative termination point for the entire prefix block.

This requirement cannot be fulfilled within Azure's current platform architecture. Azure's Software Defined Networking fabric routes public IP traffic per-individual-IP based on Azure Resource Manager resource bindings — not per-prefix. There is no API, ARM schema property, or fabric-level mechanism that allows a tenant to associate a Public IP Prefix object with a VM or NVA as a single routing target. The prefix cannot be "terminated" on an NVA in the way that a BGP-advertised prefix terminates on a router or firewall in a traditional network.

The practical consequences are: (1) the 1,024 IPs in the prefix must each be individually instantiated as separate ARM resources and individually assigned to NVA NIC IP configurations — a maximum of 256 per NIC — requiring at minimum 4 NVA instances; (2) the default subscription quota of 500 public IPs is insufficient for a full /22; (3) no single-object management of the prefix is possible for VM/NVA workloads; and (4) no future Azure quota increase or support escalation will change the underlying architectural constraint.

Legacy & Business Perspective

How It Used to Work — and Why the Team Expected This to Keep Working

For the majority of enterprise networking history, owning a block of public IP addresses meant having complete control over how traffic to those addresses was routed. If your organisation owned a /22 — 1,024 consecutive IP addresses — you could advertise that block to the internet via BGP from any device you controlled: a router, a firewall, an NVA. Traffic arrived at your edge because the internet's routing tables pointed to your device. You owned the path.

This model is simple, powerful, and well-understood. It is how internet routing has worked since the earliest days of BGP. Data centres, co-location facilities, and private network operators all work this way. When your organisation moved workloads to Azure, it was natural — and entirely reasonable — to assume this model would continue. The prefix existed. An NVA was provisioned. The assumption was that the two could be connected the same way they always had been.

In the on-premises world, a prefix block is a routing object. You own it, you advertise it, you terminate it wherever you want. The expectation that Azure would honour this model was not unreasonable — it was a logical extension of decades of networking practice.

The Expectation Gap — and Why It Is Nobody's Fault

It is worth being explicit about something: the team that built this architecture did nothing wrong. They applied sound, proven networking principles to a cloud environment, in a period when cloud providers were still evolving their networking models and when documentation on the precise boundaries of IP management was less detailed than it is today. The assumption that a prefix block could be terminated on an NVA was not unreasonable — it was simply incompatible with how Azure's SDN fabric operates.

Azure's documentation has improved significantly over the years, but the gap between "what BGP engineers expect" and "what Azure's IP services model supports" remains a consistent source of confusion. Azure Firewall and NAT Gateway — managed services — do support native prefix attachment. This creates a reasonable expectation that VMs and NVAs might eventually support the same. They do not, and there is no roadmap indication that they will.

💼 For Business Stakeholders

The core message is straightforward: the networking design that this workload relies on is not supported by Azure's platform as a standard capability. The team is not asking for something unreasonable in absolute networking terms — prefix-based routing to an NVA is normal and supported everywhere except Azure's public IP model for VMs. But Azure's platform works differently, and adapting to it requires a deliberate architectural choice. The two viable paths are (1) accept the operational cost of managing individual IPs at scale inside Azure, or (2) keep the prefix on-premises where the BGP model is native, and connect Azure workloads via ExpressRoute. Both are sound. Neither is free. The decision should be made with full awareness of the trade-offs, not deferred.

What a Resolution Looks Like in Business Terms

  • If Option A (individual IPs in Azure) is chosen: Customers keep their existing whitelist unchanged — the /22 CIDR remains valid, as all IPs are contiguously allocated from the same prefix.   • If Option B (on-premises BGP + ExpressRoute) is chosen: The external-facing architecture is essentially unchanged. The /22 continues to be advertised from on-premises via BGP exactly as before. Deep Dive

Understanding the /22 — Origins, Legacy Use, and Modernisation

To understand why this architecture problem exists, you need to understand what a /22 is, where it came from, why organisations adopted it as a standard unit of deployment, and what "modernising" it actually means in practice. This section covers all of that — starting from the 1990s.

The Origins of CIDR and Prefix-Based Routing

Before 1993, the internet operated on a classful addressing model. IP addresses were divided into rigid classes — Class A (/8, 16 million addresses), Class B (/16, 65,536 addresses), and Class C (/24, 256 addresses) — with no flexibility in between. An organisation needing 1,000 addresses would receive a Class B allocation of 65,536 because Class C was too small. This model was catastrophically wasteful and, more dangerously, was collapsing the internet's routing tables. By 1992 the BGP routing table was growing so fast that routers of the era would run out of memory within years.

Classless Inter-Domain Routing (CIDR), defined in RFC 1519 (1993), later revised as RFC 4632, solved this by replacing fixed classes with variable-length prefix notation. Instead of "Class B," an allocation could be /22 — exactly 1,024 addresses, sized to fit the actual need. The / notation means the number of fixed bits in the network mask: a /22 has 22 fixed bits, leaving 10 bits for host addresses, yielding 2¹⁰ = 1,024 IPs.

CIDR also introduced route aggregation (supernetting) — the ability to summarise multiple smaller prefixes into one route announcement. An ISP holding blocks 203.0.112.0/24 through 203.0.115.0/24 could advertise a single 203.0.112.0/22 to the internet instead of four separate /24 routes. This dramatically slowed routing table growth and remains the foundational mechanism by which the internet's BGP table stays manageable today.

Prefix Length
The number of fixed (network) bits in a CIDR block. Larger numbers mean smaller blocks: /30 = 4 addresses, /22 = 1,024 addresses, /8 = 16 million addresses.
Supernet / Aggregation
Combining multiple smaller prefixes into one larger announcement. /22 is the natural aggregation of four contiguous /24 blocks — this is one reason /22 became a common organisational unit.
RIR Allocation
Regional Internet Registries (ARIN, RIPE, APNIC, LACNIC, AFRINIC) distribute address space to ISPs and organisations. Minimum allocations were historically set at /22 for direct assignments to end-user organisations, making it the smallest independently routable block in most policy frameworks.
PA vs. PI Space
Provider-Aggregatable (PA) space is assigned by an ISP and returned when you leave. Provider-Independent (PI) space is assigned directly from the RIR and travels with you. A /22 is often the minimum size for PI allocation — the minimum block a routing registry will inject independently into the global BGP table.

Why /22 Specifically — The Practical and Policy Reasons

The /22 is not an arbitrary choice. It sits at the intersection of three factors that made it the dominant unit of mid-size enterprise IP allocation throughout the 2000s and 2010s.

RIR Policy Minimum

Most RIRs set the minimum PI (Provider-Independent) allocation at /22. This meant any organisation that wanted to multihome (connect to multiple ISPs) and maintain routing stability across providers needed at least a /22. Smaller blocks were filtered by many ISPs as a matter of routing policy.

BGP Filter Thresholds

For most of the internet's history, ISPs applied "prefix length filters" that rejected routes more specific than /24 or smaller than /22 depending on direction. A /22 would be accepted by virtually all upstream providers without question, making it the safe minimum for an independently routable block.

Operational Headroom

1,024 addresses provided comfortable headroom for medium-sized deployments. Four natural /24 subnets allow clean internal segmentation — DMZ, application tier, database tier, management — each with 256 addresses, while advertising a single aggregated route externally.

IPv4 Exhaustion Pressure

As IANA declared IPv4 exhaustion in 2011, RIRs tightened allocation policies. Late allocations were often /22 as a final, fixed block. Organisations that received a /22 at this time often built their entire external addressing strategy around it, knowing no further IPv4 space would be forthcoming.

ℹ The /22 and the Global Routing Table

As of 2024, the global BGP routing table contains over 950,000 prefixes. The vast majority of these are /24 deaggregates — individual /24s broken out from larger allocations for traffic engineering. A /22 that is not deaggregated and is advertised as a single route represents exactly the behaviour CIDR was designed to encourage: efficient, aggregated routing. In the context of this document, the team's use of a /22 as a single routing object is architecturally correct for the traditional internet routing model. It is Azure's platform that diverges from this model, not the team's design.

Why Legacy Deployments Are Built Around /22 Blocks

Understanding the historical context makes it clear why so many enterprise deployments from the 2005–2018 era are structured around a /22. The pattern was essentially universal for organisations of a certain size deploying services with external-facing IP requirements.

1
The Data Centre Era (Pre-2010)
Physical servers, BGP at the rack level, /22 as the unit of presence

In traditional data centre deployments, an organisation would obtain a /22 allocation from its RIR or upstream ISP, bring it to the co-location facility, and peer with the facility's BGP infrastructure. The prefix would be advertised from the facility's edge routers, pointing to the organisation's own border routers, which would then route traffic to physical servers.

The NVA (typically a Cisco ASA, Juniper SRX, or Palo Alto firewall) sat behind the border router, receiving traffic for the entire /22 via a single aggregate route. This is the model that works natively: BGP carries the /22 as one route, and the firewall terminates it as one policy object. Network engineers designed entire security models around this — zone-based policies, NAT rules, and application inspection were all applied at the prefix level.

  • Traffic flow: Internet → ISP → BGP advertisement of /22 → co-lo edge → organisation border router → NVA (inspects entire prefix as one object) → physical servers
  • IP management: Static assignment from a spreadsheet. No lifecycle management tooling needed — IPs were permanently bound to physical NICs.
  • Change process: Adding a server meant updating the spreadsheet and patching a cable. IP whitelisting was updated by emailing the network team.
2
The Virtualisation Era (2010–2016)
VMware, vSphere, NSX — the /22 moves to the hypervisor

As VMware and other hypervisors proliferated, the physical servers were replaced by VMs — but the network topology changed very little. VMware NSX and similar SDN platforms were designed explicitly to emulate the traditional network model within a virtualised environment. A vSphere cluster would sit behind the same border router and NVA, and VMs would be assigned IPs from the same /22 allocation.

This era reinforced the /22 model rather than challenging it. IT teams virtualised servers without redesigning networks. The NVA still terminated the full prefix. VXLAN overlays extended Layer 2 across hypervisors but kept the same external IP addressing unchanged. When organisations later attempted to lift-and-shift these environments to Azure, they assumed — again reasonably — that the same model would continue.

  • NSX-V / NSX-T: Provided logical switching and routing inside the virtualised environment, but the external BGP-advertised prefix and NVA perimeter remained identical to the physical model.
  • IP management: IPAM tools (Infoblox, BlueCat) managed allocations within the /22, but the prefix itself remained a single routing object.
  • Security model: Firewall rules referenced the /22 as a source/destination object. Micro-segmentation happened inside the cluster; the perimeter NVA still owned the prefix boundary.
3
The Cloud Migration Era (2016–Present)
Lift-and-shift to Azure — where the model breaks

When lift-and-shift migrations to Azure began in earnest, the assumption was that the same prefix-based perimeter model would translate. The /22 allocation would follow the workload, an NVA would be deployed in Azure to replace the on-premises firewall, and the BGP advertisement would be updated to point to Azure. This is the architecture that worked for fifteen years. It is the architecture that Azure cannot support for tenant-managed VMs.

The disconnect is fundamental: Azure's networking model was designed from scratch as an SDN platform optimised for resource-centric, individual-IP assignment. It was not designed to emulate the BGP-prefix-termination model of physical networks. Microsoft's managed services (Azure Firewall, NAT Gateway) do support prefix-level operations because Microsoft built bespoke fabric integration for them. That integration was never extended to general-purpose VMs.

⚠ The Lift-and-Shift Assumption Failure

The lift-and-shift migration pattern assumes network architecture is portable. For most networking constructs, it is — VLANs become VNet subnets, firewall rules become NSGs, routing tables become UDRs. The /22 prefix-to-NVA termination model is one of the few cases where it categorically is not. This is not documented prominently in Azure migration guides, which is why teams discover it late — typically during or after migration rather than during planning.

Modernising Away from Legacy /22 Dependency

Modernisation does not mean abandoning the /22 — it means decoupling the operational function of the prefix (stable external identity, customer whitelisting, routing aggregation) from the infrastructure mechanism (NVA termination of a prefix block). These are separable concerns, and modern cloud architectures separate them.

The Four Modernisation Patterns

Legacy Pattern
  • Single /22 terminated on perimeter NVA
  • All 1,024 IPs managed as one routing object
  • NVA is the single inspection and policy point
  • Customer whitelists the CIDR block against the NVA's IP

Modern Pattern
  • Prefix identity preserved; termination point changes

Pattern 1 — Preserve Prefix, Move Termination On-Premises (Recommended for Legacy)

Keep the /22 exactly where it works: on-premises. The prefix continues to be advertised via BGP from your AS. The on-premises NVA continues to terminate it. Azure workloads are connected via ExpressRoute or VPN and addressed with private RFC1918 space. From the customer's perspective, nothing changes. From Azure's perspective, workloads are simply reached via private connectivity — no public IP complexity on the Azure side.

This pattern requires no re-education of customers, no changes to whitelists, no contract amendments. The cost is an ExpressRoute circuit and on-premises NVA capacity. It is the lowest-risk modernisation path for organisations with deeply embedded /22 dependencies.

Pattern 2 — Re-platform to Azure-Native Services (Best Long-Term)

The cleanest modernisation replaces the NVA perimeter with Azure-native services that natively support prefix-level operations. This means:

  • Azure Firewall Premium as the replacement for the perimeter NVA — it accepts the /22 Public IP Prefix as a single object, applies IDPS, TLS inspection, and application rules, and exposes the entire prefix as its public-facing identity. This is the architecturally cleanest path for inspection requirements.
  • NAT Gateway for outbound SNAT using the full prefix — all 1,024 IPs available as outbound source addresses, managed as one object, with no per-IP lifecycle management.
  • Azure Front Door Premium as the global ingress layer — the /22 external identity is replaced by Front Door's globally anycast, stable IP ranges, eliminating the dependency on a specific customer-owned block.

This pattern requires customer communication (whitelists change from a specific /22 to Azure Firewall's public IPs or Front Door's service tag ranges) but eliminates all per-IP management, NVA VM operations, and prefix lifecycle complexity. It is the most operationally efficient long-term state.

Pattern 3 — Gradual Subnet Migration (Low Risk, Longer Timeline)

For organisations that cannot move everything at once, a subnet-by-subnet migration preserves the /22 external identity while progressively retiring individual IP assignments. The /22 is decomposed into its four natural /24 subnets and migrated in phases:

  • Phase 1: Migrate the least-critical /24 subnet to Azure Firewall or NAT Gateway-based routing. Validate. Communicate changes to customers for that subset of IPs.
  • Phase 2: Repeat for the next /24. Each phase reduces the IP management surface by 256 addresses.
  • Phase 3–4: Complete migration. At the end of Phase 4, the entire /22 is under Azure-native prefix management via Azure Firewall, with no per-IP lifecycle management required.

Pattern 4 — IPv6 Dual-Stack and Prefix Retirement (Long-Term Strategic)

The deepest modernisation path retires the IPv4 /22 dependency entirely by transitioning external-facing services to IPv6, supported by Azure's dual-stack VNet support. IPv6 prefixes are abundant — a standard IPv6 allocation for an organisation is a /48, providing 65,536 /64 subnets, each with 18 quintillion addresses. The IPv4 scarcity that drove the /22-as-minimum-allocation model simply does not exist in IPv6.

This pattern is a multi-year programme, not a migration. It requires customer-side IPv6 support, DNS dual-stack configuration, and application-layer changes. But for greenfield workloads or organisations willing to invest, it eliminates the IPv4 prefix dependency permanently.

✓ Modernisation Decision Summary

Short-term / lowest disruption: Pattern 1 (on-premises BGP + ExpressRoute). The /22 stays where it works. Customers notice nothing.
Best long-term cloud architecture: Pattern 2 (Azure Firewall Premium + native prefix attachment). Eliminates NVA complexity, retains prefix identity, gains IDPS and TLS inspection.
No timeline pressure / maximum flexibility: Pattern 3 (gradual subnet migration). Derisks change by splitting the /22 into four sequential phases.
Strategic investment: Pattern 4 (IPv6 dual-stack). Retires IPv4 scarcity dependency permanently.

Executive Summary

Executive Summary

⚠ Key Finding

Azure's control-plane and data-plane architecture fundamentally prevents attaching a Public IP Prefix block (e.g., /22) to a standalone Network Virtual Appliance as a single routable object. This is a platform-level constraint embedded in Azure's resource-centric IP association model — not a quota limit, a permissions boundary, or a feature gap that can be unlocked with a support ticket or preview feature. Multiple independent technical consultations and official Microsoft engineering documentation confirm this position with no exceptions.

The root conflict: the use case assumes a BGP-prefix-routing model (advertise a prefix block, terminate the entire block on a device of your choice) while Azure implements a resource-association model (individual IP addresses are bound to specific Azure resource objects; routing follows those bindings). These paradigms are architecturally incompatible within the current Azure platform.

This document explains why — at a deep technical level — and documents the available resolution paths.

Technical Requirements

Requirements & Root Conflict

Stated Technical Requirements

  • Contiguous /22 prefix exposure: A full 1,024-address block must be reachable externally as a single network range, not as a list of individual IPs
  • Customer & partner whitelisting: External parties whitelist the /22 CIDR range in their firewalls — per-IP whitelisting at customer sites is operationally unacceptable at this scale
  • NVA-based traffic control: All inbound traffic for the prefix must pass through a Network Virtual Appliance for inspection, NAT, or policy enforcement before reaching backend workloads
  • Minimal operational overhead: The team cannot sustain per-IP lifecycle management (create, assign, reassign, delete) across 1,024 IP resources
  • Legacy compatibility: The original deployment architecture predates Azure's current IP services model and relies on a BGP-native routing assumption

Why These Requirements Conflict with Azure

In a traditional on-premises or co-location environment, a /22 prefix can be advertised via BGP from any router that participates in BGP and terminated on any NVA or firewall. The NVA owns the prefix. Traffic arrives because the BGP route points there.

Azure does not expose this capability to tenants for standard public IP space. Instead, Azure's software-defined network (SDN) layer owns the BGP advertisement and makes per-IP forwarding decisions based on resource associations you configure in Azure Resource Manager. There is no API to say "send all traffic for this /22 to this NVA" — because the fabric simply does not work that way.

Azure Platform Architecture

Azure Public IP Architecture — How It Actually Works

3.1 The Azure Fabric Routing Model

Azure's public IP routing is built on a proprietary Software Defined Networking fabric. Understanding this fabric is essential to understanding why prefix termination on an NVA is architecturally impossible.

  • Microsoft AS8075 advertises all Azure public IP space to the internet. Every Azure public IP prefix — including prefixes you allocate to your subscription — is announced to the global internet from Microsoft's autonomous system. Tenants do not participate in BGP with the Microsoft edge. You cannot inject your own BGP route for an Azure public IP prefix.
  • The Azure SDN maintains a per-IP resource binding table. For each public IP address resource in your subscription, Azure's SDN records which physical host is running the associated Azure resource (VM, gateway, load balancer, etc.). When a packet arrives at the Microsoft edge destined for a public IP, the fabric performs a lookup in this binding table and encapsulates the packet for delivery to the correct host.
  • Routing decisions are made per-IP, not per-prefix. The fabric does not have a "send this prefix to this host" mechanism for VM workloads. Each /32 is routed independently based on its individual binding. A prefix is a reservation object in the control plane, not a routing construct in the data plane.
  • Host-level encapsulation. Traffic is encapsulated at the Azure edge and delivered through the fabric to the specific physical host running the bound resource. By the time traffic reaches your NVA's NIC, the fabric has already made its routing decision — routing to a VM/NVA is a consequence of the IP-to-resource binding, not something the NVA controls or influences.
  • No tenant BGP peering for public IP prefixes. Azure ExpressRoute supports BGP peering between tenants and Microsoft — but only for private address space (RFC1918) exchanged over private peering. Standard Azure public IP prefixes are not negotiable via tenant BGP sessions. The Microsoft edge advertisement is unilateral.
ℹ Architectural Implication

There is no mechanism at any layer — ARM API, Azure CLI, portal, PowerShell, or direct fabric access — for a tenant to instruct Azure to route all traffic for a prefix block to a specific NVA. The fabric routing decision is made per-IP, based on the resource binding you configure. A prefix cannot be bound to a VM NIC as a unit.

3.2 What a Public IP Prefix Object Actually Is

A Public IP Prefix (Microsoft.Network/publicIPPrefixes in ARM) is an administrative reservation object — not a routing object. When you create one:

A contiguous block of addresses (e.g., /22 = 1,024 IPs) is reserved from Microsoft's public IP pool in a specific Azure region, exclusively for your subscription.
The prefix object is stored in Azure Resource Manager with its own resource ID, SKU (Standard), and lifecycle — but it has no data-plane effect at this point. No traffic is routed. The IPs are not reachable.
To make any individual IP within the prefix reachable, you must create a separate Microsoft.Network/publicIPAddresses resource that references the prefix as its source (publicIPPrefix property). Each such resource instantiates one /32 from the block.
The individual Public IP Address resource must then be associated with a supported Azure resource (VM NIC, load balancer frontend, NAT Gateway, Azure Firewall, etc.) before the Azure fabric creates the binding and the IP becomes reachable from the internet.
🚫 Critical Constraint

Step 4 is where the fundamental constraint lives. The set of Azure resources that can be associated with a Public IP is fixed and documented by Microsoft. A VM NIC IP configuration accepts an individual Public IP Address resource — not a Public IP Prefix object. There is no ARM schema property, no REST API parameter, and no Azure portal control that associates a prefix object directly with a VM NIC.

Platform Limits

NIC IP Configuration Model & Subscription Limits

4.1 How Public IPs Attach to an NVA NIC

A VM (including any NVA) in Azure can have one or more Network Interface Cards (NICs). Each NIC maintains one or more IP configurations (ipConfigurations[] in the ARM schema). Each IP configuration is a pairing of:

  • privateIPAddress — an IP address from the VNet subnet attached to this NIC
  • publicIPAddress — an optional reference to a Microsoft.Network/publicIPAddresses resource

To assign N public IPs to a single NVA, you must create N individual Public IP Address resources and add N IP configurations to the NVA's NIC(s), each referencing exactly one Public IP Address resource. There is no bulk operation, no prefix reference, and no shorthand — this is a one-to-one relationship defined by the ARM schema.

4.2 Hard Limits & Their Impact on a /22

🚫 Hard Limit: 256 IP Configurations per NIC

As documented in Azure subscription service limits, each VM NIC supports a maximum of 256 IP configurations. A /22 prefix contains 1,024 addresses. Assigning all 1,024 IPs to a single NVA would require a minimum of four NVA instances (or four separate NICs across NVA instances), each holding 256 IP configurations. This is before accounting for management IPs, health probe IPs, or any other required configurations.

Resolution Paths

Resolution Paths

Option A Individual IP Assignment at Scale (Azure-Native)

Provision all required IPs individually from the /22 prefix, distribute them across multiple NVA instances, and automate the lifecycle via Infrastructure-as-Code. This stays within Azure's supported model but accepts significant operational complexity.

Implementation Steps

Submit a subscription quota increase request for Public IP Addresses to at least 1,024 in the target region (Subscriptions → Usage + Quotas in the portal). Allow multiple business days for approval.
Create the /22 Public IP Prefix resource in the target region via ARM/Bicep/Terraform. This reserves the contiguous block. Confirm the prefix is contiguous before proceeding (Azure guarantees this at creation time).
Instantiate N individual Public IP Address resources from the prefix (loop in Bicep/Terraform). Each resource references the prefix via the publicIPPrefix.id property. Batch this — ARM deployments support up to 800 resources per deployment.
Provision NVA VM instances — one per 256 IPs required. Use a VM SKU that supports multiple NICs. Attach one dedicated NIC per NVA instance for public IP assignment. Keep the primary NIC for management and VNet routing.
Assign Public IP Address resources to NIC IP configurations in batches of up to 256 per NIC. This must be done via ARM API or IaC — the portal becomes impractical at this scale.
Deploy a Standard Load Balancer in front of the NVA instances for inbound distribution. Note: the Load Balancer itself cannot hold the prefix object as an inbound frontend — individual frontend IP configurations are still required.
Implement lifecycle automation (Azure Functions or Logic Apps) to handle IP reassignment events — e.g., when an NVA instance is replaced or a new IP range is required. This is the largest ongoing operational cost of this approach.

Trade-offs

  • Customer whitelisting: If all 1,024 IPs are allocated contiguously from the prefix (which Azure guarantees when creating IPs from a prefix), customers can still whitelist the /22 CIDR notation. The IPs are contiguous even if they're managed individually in Azure.
  • Operational overhead: Any IP lifecycle event (adding IPs, replacing an NVA, scaling up) requires coordinated ARM API calls across prefix resources, IP resources, and NIC IP configuration resources. Robust IaC and automation tooling is a prerequisite.
  • Scaling ceiling: If the required IP count grows beyond what 4 NVA instances can support (4 × 256 = 1,024), the entire prefix is already at capacity with no headroom. A larger prefix (/21 or beyond) would require redesign.
Option B — Recommended On-Premises BGP Termination + Azure Hybrid Connectivity

Retain the /22 prefix advertisement on-premises via BGP — where a BGP-prefix-routing model is natively supported. Route traffic destined for Azure workloads through ExpressRoute or a site-to-site VPN. Azure workloads are reachable via private RFC1918 addressing through the hybrid connectivity layer.

Technical Design

  • On-premises edge router advertises the /22 to upstream ISPs via BGP (customer AS). This is the existing legacy model — no change required on the external BGP advertisement side.
  • On-premises NVA receives all /22 inbound traffic and applies inspection, NAT, and forwarding policy. Traffic destined for Azure workloads is forwarded via the hybrid link.
  • ExpressRoute circuit (preferred) or site-to-site VPN (fallback) connects on-premises to the Azure VNet via a Virtual Network Gateway. ExpressRoute provides deterministic latency and bandwidth guarantees; VPN provides simpler setup at lower cost.
  • Azure Route Server (optional) can be deployed in the hub VNet to propagate on-premises BGP routes into the Azure VNet routing table, enabling dynamic routing for spoke VNets without manual UDR management.
  • Azure workloads use private IP addresses within the VNet. No public IPs are exposed on the Azure-side NVA. Workloads are reachable because on-premises forwards traffic over the ExpressRoute/VPN after its own inspection/policy decisions.
✓ Why This Is the Recommended Path

This design resolves the conflict by matching each environment to its native routing model: the /22 prefix lives in a BGP-routing environment (on-premises) where it belongs architecturally, while Azure workloads live in Azure's resource-centric IP model. No Azure architectural constraint is violated. The legacy deployment model is preserved on the on-premises side. No quota increase request is required for public IPs in Azure.

Trade-offs

  • Requires an active ExpressRoute circuit or site-to-site VPN with sufficient bandwidth for all /22 traffic volume. ExpressRoute circuits carry monthly costs based on bandwidth tier.
  • On-premises NVA capacity must be sized to handle the full /22 traffic load — the on-premises NVA becomes the single point of inspection for all inbound traffic.
  • Introduces an on-premises infrastructure dependency for Azure workload availability. ExpressRoute SLA is 99.95%; backup VPN is recommended for resilience.
Option C Azure Front Door / CDN with Published Service Tag Ranges

If the /22 requirement exists solely to provide external parties with a stable, whitelistable IP range — not for BGP control or NVA-level inspection — Azure Front Door or Azure CDN may serve as an alternative ingress layer.

Azure publishes its service tag IP ranges (including AzureFrontDoor.Frontend) weekly as a downloadable JSON file. External parties can whitelist these published ranges instead of a specific customer-owned prefix. Microsoft maintains the IP range file and publishes updates 1 week before any change takes effect.

  • Decouples customer whitelisting from infrastructure-level prefix management entirely
  • Front Door provides global anycast ingress, DDoS protection, WAF, and TLS termination as managed capabilities
  • Applicable only if the primary driver is whitelisting stability — not IP ownership, specific NVA inspection, or BGP route control
  • Not applicable if customers require whitelisting a customer-owned CIDR range specifically (e.g., contractual requirements)
Technical Q&A

Technical Q&A

Can Azure Route Server be used to advertise the /22 from an NVA to the internet?

Azure Route Server enables BGP peering between an NVA and Route Server to exchange routes within the Azure VNet. Routes learned from the NVA via Route Server are propagated into the VNet routing table — affecting how VNet traffic reaches spoke networks or on-premises via ExpressRoute/VPN. Route Server does not have a path to the Microsoft internet edge. Routes advertised by the NVA to Route Server do not become internet BGP announcements. The Microsoft edge advertisement (AS8075) is completely separate and not influenced by Route Server.

Can a User Defined Route (UDR) force inbound internet traffic for the /22 to the NVA?

User Defined Routes operate within the Azure VNet routing domain. They affect how traffic is forwarded between subnets, VMs, and gateways after it has been delivered by the Azure fabric to the VNet. UDRs cannot influence how the Azure fabric routes inbound internet traffic to public IP addresses — that decision is made by the fabric's per-IP resource binding table before the packet enters the VNet. UDRs are effective for east-west (internal VNet) traffic and for directing traffic to an NVA after it has been received on a VM NIC, but they do not affect north-south public IP ingress routing.

Can a Standard Load Balancer frontend hold the prefix and distribute to NVA backends?

A Standard Load Balancer can reference a Public IP Prefix in outbound rules for SNAT — this allows all IPs in the prefix to be used as source addresses for outbound connections from the backend pool. This is an outbound-only construct. For inbound load balancing, the Load Balancer frontend still requires individual Public IP Address associations — one per frontend IP configuration. The Load Balancer cannot accept a prefix object as an inbound frontend. Additionally, even if individual IPs are assigned to Load Balancer frontends, the traffic is load-balanced to backend pool members (the NVAs), not terminated on the NVAs as a prefix block.

Does Azure Virtual WAN offer any path around these constraints?

Azure Virtual WAN does not change the Public IP Prefix attachment model for NVAs. Third-party NVAs deployed in a vWAN hub (via the Integrated NVA in hub feature) are still subject to the same NIC IP configuration constraints. vWAN provides managed hub-and-spoke routing — it does not expose prefix-level routing to tenant-managed VMs and does not give NVAs any special ability to receive prefixes as single routing objects.

Is this constraint on the Azure roadmap to be resolved?

As of this document's date, there is no public Azure roadmap announcement or Azure Feedback (UserVoice) roadmap item indicating that VM/NVA direct prefix attachment is planned. The constraint is deeply architectural — it would require changes to the Azure SDN fabric's per-IP resource binding model, which is foundational infrastructure. Azure Firewall and NAT Gateway have native prefix support because Microsoft built purpose-built fabric integration into those managed services. That integration path does not exist for general-purpose VMs. This is not a short-term roadmap item.

What happens if we request a support ticket from Microsoft to enable this?

A Microsoft support ticket would confirm the same position documented here. This is not a configuration that Microsoft Support can enable for a specific subscription — it is a platform-level architectural constraint, not a per-subscription feature flag. Support engineers would direct the engagement toward the documented alternatives (Azure Firewall, NAT Gateway, on-premises BGP termination). Escalating to Azure engineering via a support case would produce the same outcome; there is no backend toggle that enables prefix-to-VM attachment.

Optimization Patterns

Whichever option is chosen, the following patterns apply to improve performance, reduce cost, and increase operational resilience.

Performance Optimizations

Accelerated Networking

Always enable enableAcceleratedNetworking: true on all NVA NICs. This offloads packet processing to the SmartNIC, reducing CPU overhead and latency. Supported on most VM SKUs of D/E/F series and above. Required for NVAs handling >1 Gbps.

NVA VM SKU Selection

Choose VM SKUs with high NIC counts and network bandwidth. The Dv5/Dsv5 series supports up to 8 NICs and 12.5 Gbps. For Option A with many IP configs, a dedicated NIC per 256-IP block avoids ARM update conflicts during scaling events.

Zone-Redundant Deployment

Deploy NVA instances across Availability Zones (1, 2, 3) and front them with a zone-redundant Standard Load Balancer. Use "zones": ["1","2","3"] on the VM and Public IP resources. Distribute IP configs evenly across zones — 85 IPs per NIC per zone for a 256-IP block.

ExpressRoute FastPath (Option B)

Enable ExpressRoute FastPath on the VNet Gateway (expressRouteGatewayBypass: true on the connection). FastPath bypasses the gateway for data-plane traffic, reducing latency by ~1ms and removing the gateway as a throughput bottleneck.

Cost Optimizations

Right-Size the IP Count

Do not instantiate all 1,024 IPs from the /22 upfront. Audit actual usage: if only 200 IPs are actively serving traffic, instantiate 256 (one NIC's worth) initially. Azure guarantees contiguity within the prefix — unused IPs reserved but not instantiated carry no per-IP charge.

Reserved Instances for NVAs

NVA VMs running continuously qualify for Azure Reserved VM Instances — 1-year or 3-year commitments saving up to 72% vs. pay-as-you-go. For stable NVA workloads, this is a near-zero-risk cost reduction.

ExpressRoute Local SKU (Option B)

If on-premises and Azure are in the same metro area, ExpressRoute Local provides unlimited data transfer at a fixed port fee — significantly cheaper than metered Standard/Premium for high-volume traffic.

Public IP Cost Awareness

Standard Public IP Addresses carry a per-hour charge when associated with a running resource. Unassociated (allocated but not attached) IPs also accrue cost. Use Azure Cost Management to tag all prefix-derived IPs and monitor spend with a prefix-block:/22 tag filter.

Operational Automation — IP Lifecycle Management (Option A)

The largest ongoing cost of Option A is IP lifecycle management. The following pattern uses an Azure Function to automate IP reassignment when an NVA is replaced or scaled.

Python (Azure Function) ip_rebalance.py — Auto-reassign IPs when NVA NIC capacity changes 
# ip_rebalance.py — Azure Function triggered by VM health event
# Trigger: Azure Monitor alert → Event Grid → this Function
# Purpose: When an NVA instance is replaced, reassign its IP configs to the new NIC

import azure.functions as func
import logging
from azure.identity import DefaultAzureCredential
from azure.mgmt.network import NetworkManagementClient
import json

app = func.FunctionApp()

@app.event_grid_trigger(arg_name="event")
def rebalance_ips(event: func.EventGridEvent):
    data = event.get_json()
    logging.info(f"NVA event received: {data.get('eventType')}")

    credential = DefaultAzureCredential()
    client = NetworkManagementClient(credential, SUBSCRIPTION_ID)

    # 1. Identify orphaned IPs (associated with deleted/stopped NIC)
    orphaned_ips = [
        pip for pip in client.public_ip_addresses.list(RESOURCE_GROUP)
        if pip.tags.get('prefix-block') == '/22'
        and pip.ip_configuration is None          # Not attached to any NIC
    ]
    logging.info(f"Found {len(orphaned_ips)} orphaned IPs to reassign")

    # 2. Find target NIC with available IP config capacity
    target_nic = find_nic_with_capacity(client, max_configs=256)
    if not target_nic:
        logging.error("No NIC has available IP config capacity. Scale out NVA first.")
        raise Exception("Capacity exhausted")

    # 3. Reassign orphaned IPs to target NIC in batches
    for pip in orphaned_ips:
        new_config = {
            "name": f"ipconfig-rebal-{pip.name}",
            "private_ip_allocation_method": "Dynamic",
            "public_ip_address": {"id": pip.id},
            "subnet": {"id": target_nic.ip_configurations[0].subnet.id}
        }
        target_nic.ip_configurations.append(new_config)

    # 4. Apply updated NIC config atomically
    client.network_interfaces.begin_create_or_update(
        RESOURCE_GROUP, target_nic.name, target_nic
    ).result()
    logging.info(f"Reassigned {len(orphaned_ips)} IPs to {target_nic.name}")


def find_nic_with_capacity(client, max_configs=256):
    """Find a NIC tagged for prefix IP assignment with available slots."""
    for nic in client.network_interfaces.list(RESOURCE_GROUP):
        if nic.tags.get('role') == 'nva-public-nic':
            current = len(nic.ip_configurations)
            if current < max_configs:
                logging.info(f"Target NIC: {nic.name} ({current}/{max_configs} configs)")
                return nic
    return None
